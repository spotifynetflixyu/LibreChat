# Steel 原檔與資料列對照介面

狀態：需求訪談已收斂，完整設計草案待使用者確認共同理解；尚未開始實作。下方技術方案為實作前提案。

依後續 `to-spec` 要求整理的完整規格見 [Steel 原檔對照與人工覆核規格](../specs/2026-10-03-steel-source-review.md)；主要驗收邊界已確認須同時證明 UI 與 DB 正確。本文保留訪談決策與程式核對紀錄。

## 已確認需求

- 僅在後端確認身分的 `ocr_result` 與 `system_order` Markdown 表格提供本功能；開啟後依按鈕所屬表格顯示對應種類的資料列。其他 Markdown 不提供對照／修正功能。
- 支援多份 PDF 與圖片，可選擇檔案及 PDF 頁碼。
- 使用大型彈窗，並可放大為全螢幕。
- 上方顯示所選 PDF 原檔頁面或圖片，下方只顯示目前檔案與頁面對應的資料列。
- 支援修改資料列並儲存到 DB。
- 保留原版 Markdown；對照介面的資料列呈現修改前後內容，沿用目前 Markdown update UI 的刪除線效果。
- 開啟按鈕所屬的那張表；舊版本只供唯讀對照，只有同一聊天中各自最後輸出的 `ocr_result` 與 `system_order` 結果可修正及儲存。人工操作不得改寫舊版聊天文本。
- 可修改、新增與刪除資料列。
- 業務欄位可修改；既有可靠來源與頁碼預設唯讀。舊資料缺少或具有不可靠來源關聯時，允許手動選擇或更正來源檔案、頁碼以標記來源，並自動儲存；仍可留空。
- 新增列自動附上目前選擇的來源檔案與原檔頁碼。
- 支援 undo／redo，涵蓋修改、新增與刪除；復原與重做也寫入 DB。操作歷程限本次彈窗開啟期間，關閉重開後重新開始，但原版與最新結果仍保留。
- 每次修改儲存格後自動儲存到 DB。
- 人工覆核每次 save 都顯示 caption，說明此次會更新多少 rows；計算此次儲存的實際列差異，包含新增、刪除及重算連動，不使用相對 AI 原版的累積差異列數。
- OCR 的尺寸、數量或材料增刪儲存後，保留既有報價供對照並標記過期；由使用者手動啟動重新報價。
- 資料列的來源檔案、頁碼或其關聯允許空值；缺值是合法資料狀態，不顯示為錯誤，也不阻擋開啟、編輯或儲存。保留原列與空值，不猜測補值或歸到某個檔案／頁面。
- OCR 與 system order 的修改、新增、刪除只更新所屬表格；system order 修改不反寫 OCR。
- 缺少可靠來源或頁碼關聯的資料列放在「未定位列」清單；可以從該處人工標記來源，完成關聯後列入對應檔案／頁面。
- 人工標記來源使用 menu selector，沿用現有選擇元件。檔案從既有檔案選項選取，頁碼從所選檔案的既有頁面選項選取，保留空值選項。
- OCR 編輯直接修改聊天訊息中的文字 Markdown，不只更新彈窗或 canonical state；同時保留原版與累積差異。
- system order 編輯後自動重算 customer_quote；system_order 與 customer_quote 都直接修改聊天訊息中的文字 Markdown。
- save 前依本次修改欄位統一重算 system order 的重量、總數及 customer_quote；不在每次輸入字元時重算，也不無條件覆蓋手動值。customer_quote 沿用現有小計與加總規則；不重新查價。缺少總數或單價時，小計可留空。
- 長度、寬度、厚度、單重、數量可觸發重算。尺寸改動重算單重及總重；手動修改單重時保留該輸入，只重算總重；數量改動保留單重，重算總重及受影響的加工總量。
- 保留現有 Markdown 欄位，不新增總重欄；kg 計價材料的總數代表總重，其他單位的總數依各自計價基準，不拿重量覆蓋。
- 單重／重量與總數仍可手動修改。總數或單價修正更新 customer_quote，不因 save 本身重新推導單重；手動總數在未觸發其依賴重算時保留。
- system order 包含材料列與加工列；加工列必須綁定對應材料，保存明確關係，不能只靠前後列位置判斷。
- 刪除材料時一併刪除綁定加工列，保留整組刪除線；undo 一次恢復整組。
- 新增或更正加工列歸屬時使用材料 menu selector；在材料下新增加工列時自動綁定。加工列的來源檔案與頁碼跟隨材料，修改綁定時同步更新。
- 缺少重算依據時保留輸入，受影響且無法計算的結果留空並標示待補，仍允許保存。不猜數值，也不沿用失效的舊結果。
- 每列最多關聯一份 PDF 的單一原檔頁碼，或單一圖片，不會同時綁定多檔、多頁或多圖；檔案與頁碼仍可缺值。
- 同一 PDF 頁面或同一圖片可綁定多個 rows，頁面下方顯示本表所有對應列；來源關聯不是一對一，不限制同一頁／圖的列數。
- 版本衝突不覆蓋新版，保留尚未儲存的修改，核對最新版後再套用。網路儲存失敗保留修改並提供重試。
- 刪除列保留刪除線供對照；目前有效資料與 customer_quote 計算不包含已刪除列。
- 檔案 menu selector 列出同一聊天已上傳且使用者可存取的 PDF／圖片。
- 第一版是頁面級對照，提供選檔／頁、上一頁／下一頁、縮放與平移；不包含零件框定位。
- system order 的型號與品名規格使用 async search selector；輸入 keyword 從後端取得可用候選，選取後才更新型號及相應資料。兩個欄位共用同一候選選擇關係，避免型號與名稱指向不同項目。
- 材料與加工 async selector 的候選價格只取目前報價 customer tier 對應的價格；該 tier 缺值時顯示並保存空值，不 fallback 到其他 tier、不沿用舊單價，也不以 0 代替。候選仍可選取並保存，customer_quote 的該列小計留空。
- 更換材料候選時不保留舊成品尺寸，長度、寬度、厚度改以所選候選的明確尺寸為準；數量保留。候選未提供明確尺寸的欄位留空，不沿用舊候選尺寸或以範圍中間值猜測。
- 更換材料候選時既有加工列保留不動：保持列身分、材料綁定、加工候選、計算輸入、總量及單價，不自動刪除、重選、重新檢查適用性或改寫加工欄位。此候選更換操作不觸發既有加工重算；之後獨立修改數量、尺寸、加工輸入或材料綁定，仍依原定觸發規則處理。
- DB 分別保留 AI 最新完整 Markdown 與人工覆核後的有效 Markdown，作為比較人工修改的兩份資料。AI 輸出新完整表或只含更新 rows 的 update Markdown，仍由後端判斷並 merge，再更新 AI 最新完整 Markdown；人工修改不寫入 AI 輸出基準。
- AI 基準更新時保留已保存人工修正供覆核；未人工修改內容採用新 AI 結果。衝突格比較最新 AI 值與人工值，只有明確採用 AI 才取代人工修正。
- 人工修正的完整 OCR Markdown 與 AI 最新完整 OCR Markdown 分別保存 DB 更新時間。下次報價取更新時間較新的版本：人工時間嚴格大於 AI 時間時取人工，AI 較新或相同時間時取 AI；開始報價時固定所選 Markdown 與版本。
- 核心審查項目：後端精準更新聊天歷史中的指定 Markdown；其他聊天、其他訊息、其他表格及目標表格以外的內容不能被修改。

## 完整介面與操作

聊天中後端確認為 `ocr_result` 或 `system_order` 的表格操作列新增對照按鈕，不能因一般表格的欄位或標題相似就提供此功能；`customer_quote` 與其他 Markdown 均不提供此功能。按鈕綁定所屬訊息與表格；開啟 OCR 表時只操作該 OCR 結果，開啟 system order 時只操作該報價，不混入其他表的列。兩種結果各自判定最後輸出，不以整則訊息的新舊或兩種結果共用一個時間判定。舊版可閱讀與對照，介面明確呈現唯讀，不提供編輯、新增、刪除、來源修正、候選更換及 undo／redo 寫入操作；不能儲存或初始化人工編輯資料而改寫舊版聊天文本。目前表格的使用者自動儲存仍屬同一版結果，不會讓自己的彈窗立即變成舊版。

可編輯資格由後端最後成功完成輸出的結果身分及 owner 決定，不能由 client 的 DOM 順序、訊息時間或最新人工更新時間推定；只有 update rows 的 AI 輸出仍由後端 merge 並確認完整結果 owner。新結果完成後，前一結果立即失去修正資格。若原本可編輯的彈窗仍開著，保留未保存操作並轉為唯讀，提供開啟最新結果；不自動把操作套到另一張表。`customer_quote` 僅依最後 system order 的儲存連動更新其明確綁定區段。

彈窗頂部包含檔案 selector、頁碼 selector、翻頁、縮放、undo／redo、全螢幕與關閉操作，以及自動儲存狀態。中間為原檔單頁預覽，下方為目前檔案與頁面對應的可編輯列；「未定位列」有獨立清單。窄螢幕仍維持上圖下表，表格允許橫向捲動；沿用 shared primitives、語意主題、本地化、鍵盤及 reduced-motion 行為。

PDF 頁碼採原檔從 1 起算；圖片視為單頁，第 1 頁。沒有可預覽檔案或尚未選檔時，仍能檢視未定位列；來源缺值不呈現錯誤。檔案本身已不可存取時，顯示無法預覽的狀態，保留資料列供閱讀與編輯，不能藉 selector 取得其他聊天或未授權檔案。

現有儲存格在完成編輯（Enter 或離開欄位）後自動儲存；來源 selector 選項變更、新增、刪除及 undo／redo 也自動儲存。不同頁面顯示的是同一份編輯狀態，切檔或切頁不丟失正在等待儲存的修改。一般關閉先完成已提交操作；有儲存失敗或尚未提交內容時，保留內容並提供重試、繼續編輯或明確捨棄選擇。

### 此次 save 的 rows caption

沿用自動儲存，每次提交準備完成後，在儲存狀態旁顯示「此次將更新 N 列」，不增加逐次確認流程。OCR 顯示該表數量；system order 分開顯示「此次將更新 system order N 列、customer_quote M 列」，材料與加工同屬 system order 的列數，避免把連動報價列混成同一張表的數量。可附「修改 X／新增 Y／刪除 Z」明細；customer_quote 總計變動另列說明，不冒充一筆品項列。

此次數量依該表最後成功保存狀態與本次完成重算後的待保存結果比較，同一穩定列身分即使改多格或同時受到手動及推導修改，也只計一次。包含來源標記、候選更換、材料／加工連動與 undo／redo 實際造成的列變更，不限目前預覽頁。沒有實際列差異時顯示 0；在同批次新增後又刪除且沒有淨變更的列不計入。原版累積差異仍獨立保留，不能拿來充當此次 save 的列數。

後端在 save 前重算並產生該次操作及預期 revision 對應的列數摘要，caption 與正式提交共用同一份已核對結果，不能先顯示人工改動列數、提交時才另外加入未計數的連動列。摘要尚未準備完成時顯示準備中，不猜數字；成功後呈現實際「已更新 N 列」並保留最近一次摘要。失敗或衝突時不顯示成功列數，保留待保存摘要與操作；核對新版後重新準備並更新 caption，不沿用舊 revision 的數量。舊版唯讀只顯示唯讀狀態，不顯示可儲存的 caption。

新增列放在目前選取列後；未選列時放在目前頁面最後一列後，沒有對應列則放在表格末尾。自動附上目前檔案及單頁，無來源選擇時允許空值。新列依原表欄位建立，不增刪欄位。業務欄位直接編輯，舊資料的來源补標／更正透過既有 menu selector；可靠來源預設唯讀。

system order 分別提供新增材料與新增加工操作。新加工必須選擇本表尚未刪除的材料；從材料操作新增時直接綁定該材料，加工來源優先跟隨材料，即使預覽正位於另一頁，也不改採預覽頁。加工列顯示在材料後，排序不代替穩定綁定。已有列的材料／加工身分不隨自由文字變動；跨身分變更需新增正確種類再刪除原列，不讓改類別文字造成隱性轉換。舊資料無法確認身分或加工歸屬時保留原列，提供類別／材料標記入口，不猜測綁定。

async selector 使用現有共享選擇元件與 React Query，依材料／加工種類查詢可用候選；加工候選另外依綁定材料核對適用性。處理 loading、empty、失敗／重試與鍵盤選取，取消或忽略過期 keyword 回應。keyword 是查詢草稿，只有選取候選才提交欄位變更；API 不把任意 keyword 當作有效 ERP 型號。後端取得選項與正式選取驗證都維持使用者、tenant、聊天與目前表格範圍。

此查詢是使用者操作的專用 catalog API，keyword 可搜尋型號、品名與規格；不直接把 UI 請求送進 AI 的 `search_price_candidates` schema，也不修改其既有工具可見性、H 型鋼或 keyword 規則。重用 repository 的參數化查詢、candidate types 與安全欄位投影，正式選取只接受候選 ID 及預期表格版本，由後端重新驗證可用性、材料／加工種類、適用性及價格，不能信任 client 傳回的任意單價或計算依據。

選取候選時將候選 ID、ERP code、品名／規格、類別、材質、單位、公式及可用計算依據保存為可重現的快照。搜尋顯示及正式選取的單價都只取該報價已確認的 customer tier（A–F）對應值，由後端讀取可信客戶快照核對，不能讓 client 任選 tier。該 tier 價格缺值時，材料與加工候選皆顯示缺價且仍可選取，保存的單價留空，不使用 repository 的其他 tier fallback 價格、不沿用舊候選或人工單價，也不以 0 代替；該列 customer_quote 小計留空，仍允許保存。合法的 0 價與空值分開。

候選的品項有效性、材料／加工種類與適用性仍需驗證，但不能僅因目前 tier 缺價而排除候選；既有 quoteEligible 或 priceSource 若依 fallback 推導，不能直接用作此 selector 的缺價過濾或單價來源。取得價格失敗是操作失敗，不能偽裝成成功取得空價。更換候選是明確更新候選價格的動作，其他尺寸／數量修改不重新查價；這個專用 UI 契約不修改既有 AI 查價流程的 fallback 規則。搜尋有分頁或截斷狀態，限制與 timeout 沿用既有設定；新增後端限制須納入專案 config schema。

選取新材料候選同步更換明確的長、寬、厚尺寸，不保留原成品尺寸；保留件數及來源。候選尺寸只有範圍或缺值時，對應欄留空，不把 min／max 當成確定尺寸、不拿旧欄補齊。候選 stock 長度有明確值時依使用者決策採候選長度；profile 厚度依現有材料規則及候選明確 web／其他厚度資料映射。尺寸、單重依據、候選單價與新的有效結果一併保存，不讓型號已換但其他欄位仍指向舊品項。

這次材料候選更換只更新材料及其衍生客戶報價，既有加工列完整保留，不因新材料尺寸或類別自動重算加工、不要求重新選取或重驗其候選適用性。其列身分、材料綁定、候選、計量模式／輸入、總數及單價保持原值；caption 不把未改動加工列計為更新。加工來源仍跟隨同一材料，因本次保留材料來源而不變。使用者之後明確選取新加工候選時，才按當時材料驗證適用性；其他獨立修改依既有重算觸發規則處理。

undo／redo 以一次完成的改格、來源標記、新增或刪除為一步，限本次彈窗開啟期間；每步產生反向或重做的 DB 操作，不把整份原版覆蓋回去。新增列、原版列與刪除列有穩定身分，不能只靠頁面中重新排列的列號識別。

## 原版、差異與有效資料

保留各版 AI 輸出的原文與後端 merge 後的最新 AI 完整 Markdown，另保存人工覆核後的有效 Markdown。當前人工累積差異相對最新 AI 完整基準，歷史基準與人工版本保留供舊版閱讀。修改格呈現人工／有效新值與刪除線 AI 基準值；AI 基準列被人工刪除後保留整列刪除線與刪除標記。人工新增列標示新增；新增後再刪除時不形成 AI 基準的刪除差異，但本次 undo 仍可恢復。有效值與最新 AI 基準相同時，對應人工差異消失。

AI 回覆與 UI 編輯使用不同的寫入來源：UI 只能更新人工有效結果，不改 AI 基準；AI 完整／update Markdown 通過既有格式、更新列與版本驗證後，由後端 merge 形成新的 AI 完整基準，省略列不視為刪除，明確刪除沿用相應協定。AI update 是完整更新列，不把前端 diff、人工刪除線或缺省欄位當成 AI 的資料。

AI 基準更新後套用已保存人工操作：未人工修改的值採用新 AI，已有人工修正的值保留並與新 AI 比較；人工新增、刪除及來源標記同樣保留其操作身分。對衝突格提供採用 AI 值操作，明確採用才解除該格人工覆寫；目前值剛好與 AI 相同時視覺差異消失，但不以數值相等推定使用者放棄其人工選擇。undo 恢復的是該步前的值與欄位來源狀態。

這個套用結果是覆核介面的比較／待保存內容，不能因 AI 基準更新就改寫最後一次人工保存的完整 Markdown 或刷新其時間。人工 OCR Markdown 只有使用者完成新的人工 save、undo／redo 或採用 AI 操作並成功提交時才更新；AI merge 只更新 AI 完整基準與 AI 保存時間。兩份最後成功保存的完整內容與時間分開，避免自動比較讓人工版永遠比 AI 新。

候選選取保存整組一致的人工變更（候選 ID、型號／品名、候選欄位、尺寸及計算依據），不能在 AI 更新時只保留型號卻換掉對應品名或依據。重算依套用後的有效輸入執行；AI 原文及 merge 完整基準不被人工計算值反向改寫。

新 AI 列與人工列有可確認對應時延續穩定 row ID。重複件號等情況若無法可靠匹配，不猜列對應，也不把新 AI 組與舊人工組同時加入有效資料造成重複計價；保留受影響人工組供對照及人工配對／採用，再將新基準套用於該組。未保存本地操作仍以 revision CAS 保護，與已保存人工操作的基準更新政策分開。

有效資料排除已刪除列及所有刪除線舊值，供 canonical state、customer_quote 計算及後續 AI 使用。聊天訊息文字保存使用者要求的最新 Markdown 與累積差異；兩者由同一次儲存更新，不能把顯示用刪除線 Markdown 再解析成有效數值。

OCR 修改同步有效 OCR 狀態與聊天文字，讓以舊 OCR 為依據的報價過期，保留舊報價內容。來源補標不自行改寫尺寸、數量或其他業務值。system order 修改只更新自己的有效報價與聊天文字，不反寫 OCR；save 前先統一重算材料及其綁定加工列的重量／計價總數，再產生 customer_quote，最後保存相關狀態與聊天文字。小計沿用現有向上取整規則；單價或總數缺值保留空白小計，總計沿用現有可計算小計加總方式。

### 下次報價的 OCR 來源選擇

後端比較兩份完整 OCR Markdown 成功提交的 server DB 時間。人工版存在且時間嚴格大於 AI 版時選人工；AI 較新、時間相同或没有人工版時選 AI。來源空值仍合法，不以來源完整度改變這個規則。只有人工版可用時取人工；兩份都不存在則維持既有缺少訂單的準備流程。

報價 admission／preflight 保存所選來源種類、內容 hash、版本及更新時間，形成該 run 的不可變輸入；child、resume、weight／customer_quote 與完成判斷都用此快照，不逐步重選來源。啟動交易核對兩份 revision，避免比較與啟動之間資料變更。介面可保留較舊人工修正供比較，但它不因此自動成為下一次報價來源；實際人工 save 成功更新時間後才重新參與選擇。

### save 前的重算觸發

| 修改項目 | 重算行為 |
| --- | --- |
| 長度、寬度、厚度 | 依確認的材料規則及計算依據重算單重，再重算總重／相關計價總數；加工量只有在其規則依賴該尺寸時重算。 |
| 手動單重 | 保留明確輸入的單重，以此重算總重／相關計價總數，不反向覆蓋單重。 |
| 數量 | 保留單重，重算總重及依件數計量的加工總量；已是整批量的值不再次倍乘，刀數依已確認方案。 |
| 手動總數／重量結果 | 保留本次手動修正，用有效總數更新 customer_quote；後續修改依賴尺寸或數量時，才依觸發規則重算。 |
| 單價 | 保留修正單價，重算 customer_quote，不查價、不重算材料單重。 |
| 更換材料候選 | 更新材料候選、明確尺寸、單重依據及該 tier 價格，重算材料結果與 customer_quote；既有加工列全部保持原值，此操作不觸發加工重算。 |
| 來源檔案、頁碼、材料綁定 | 來源變更不推導尺寸或重量；加工改綁材料時依新材料的已確認輸入及加工計量規則更新相關總量。 |

加工計算需保留「每件量／整批量／方案量」及已確認的計算輸入，不能從舊總數倒推每件量。孔數、折數、槽數、加工長度與切工刀數分別遵守現有類別規則；沒有相應依據時受影響的計算結果留空。這些輸入須有結構化保存與 UI 可補填入口，不只寫在自由文字備註。

### 欄位依據、數值與失效規則

每個計算相關值保存來源（候選、明確手動輸入、推導結果或舊資料），推導結果記錄所依據的輸入版本與規則版本。尺寸或材料候選／類別／計價單位變更，使先前單重及相關總數的覆寫失效，依新依據重算；數量變更保留單重，只使總重及按件計量的加工總量失效。手動總數保留到其依賴輸入改動；手動單價不因尺寸或件數變更而被重新查價覆蓋，明確選取新候選才更新其候選單價。

手動單重優先於本次沒有新的尺寸或材料變更的推導；手動總數優先於本次沒有依賴輸入變更的推導。操作按順序套用，同一儲存批次最後一次明確手動修正優先；後續依賴輸入再變更才重新失效。清空單重或數量時，保留空值並清空受影響的推導總數；清空必要尺寸使尺寸依據不足，相關推導結果留空。未觸發該依賴的舊列不因重算流程存在而被全部清空。

數值採規範十進位字串與精確十進位運算，不能把 JavaScript 浮點結果作持久化計算依據。空值與 0 分開，合法的 0 不視為缺值；保留手動／推導來源。數值欄非合法數字時維持編輯草稿並提供欄位校正，不提交假數字；空值可提交。重量與計價量保留規則要求的精確結果，customer_quote 小計才沿用既有逐列向上取整，總計加總這些有效小計。

加工明確保存所屬材料 ID、加工類別、候選資料快照、規則版本與計量模式。每件模式保存每件量並讀取材料件數；整批模式保存確認的整批量；切工方案模式保存確認的母材／stock 長度、成品長度、件數、配料配置、餘料、頭尾修整及方案版本或不可變參照，才依切工規則計算刀／片數。沒有這些依據時受影響結果留空，不能只由舊總數或備註數字推測。加工列有展開的計算資料區可補填已確認的計量模式與輸入，不更動現有 Markdown 欄位。

### 修改範圍與一致性邊界

每張可編輯表格綁定邏輯結果 lineage、AI 基準版本、人工 revision 與目前訊息／content part／section；system order 另綁定其報價 run、基準 OCR lineage／revision、客戶快照及唯一 customer_quote section 位置。同一邏輯结果的新 AI 完整／update 基準可重新套用已保存人工操作；不同報價 run 或客戶的歷史人工價不自行搬到新報價。OCR 修改讓依該基準 OCR 的有效報價快照及對應 system order／customer_quote 呈現過期，保留其他歷史版本及其他訊息區段，不把同一聊天所有報價視為同一份資料。

儲存要先驗證目標 table 與衍生 quote 的 section 仍屬同一有效 lineage。customer_quote 的 section 缺少時，從該報價保存的明確 owner 位置重建；找不到可信 owner 或內容已被別的結果取代時，回傳版本衝突並保留本地修改，不另挑聊天中名稱相同的表格。修改只替換管理中的表格 section，保留原訊息其他正文、附件、manual review 與 metadata。

### 聊天 Markdown 精準更新：獨立審查項目

寫入定位必須包含 authenticated user／tenant、conversation ID、message ID、content part 身分、邏輯表格身分、section／table 位置，以及預期訊息與表格版本。後端從已授權且仍有效的 DB 訊息核對 locator 與目前表格 hash，定位唯一的 Markdown 表格範圍；不能只按 `ocr_result`／`system_order` 標題搜尋、找到第一張同名表就替換，也不能用新舊字串全域 replace。

每次人工寫入在同一交易／CAS 邊界重新核對：target 是該聊天最後輸出的所屬種類結果，而非僅為某個 lineage 的最新人工 revision。舊版或其他 Markdown 即使提交正確 hash、重試操作 ID、undo／redo 或自行呼叫 API，也不得寫入；新結果與儲存並發時必須拒絕已失去資格的操作。唯讀開啟與查詢不得改寫歷史訊息，舊版人工差異依其既存快照顯示，不回填成最新聊天文字。

寫入服務先建立此次允許修改的明確 target 清單：人工 OCR 表、或人工 system order 與其已綁定的 customer_quote；必要的衍生表格也必須有可信 owner，不能以整份聊天為替換範圍。僅替換 target 範圍，保留其前後原文、空白、換行、其他表格、code fences、說明、來源附件與非文字 content parts；不重新格式化整則訊息或重建整份聊天。

同一訊息如果有多張同名或完全相同內容的表格，必須依穩定表格身分及預期版本定位；沒有可靠 locator、表格已移位且無法核對、目標被移除或 mirror 表示不一致時，回傳安全衝突並保留人工操作。若訊息同時有 `text` 及 `content` 的表格表示，核對其 target mirror 關係，只同步相應 target，不能覆寫其他 content parts。client 的 DOM index、標題或 offset 不能直接作為 DB 更新權限或可信位置。

交易保存條件同時包括 user／tenant／conversation／message 及 revision。並發新增正文、另一表格修改、AI 更新或訊息編輯不能被舊的整則文字覆蓋；重新讀取後仍需核對目標版本，不使用搜尋同名表作為失敗 fallback。重試、undo／redo、候選選取與 AI merge 都經同一精準寫入邊界。

程式審查需有獨立 reviewer 檢視這個寫入路徑，驗證：

- 兩個聊天有相同 Markdown 時，只更新指定聊天的指定表格。
- 同一聊天多個訊息有同名表、同訊息有重複表、code fence 內含同樣標題時，只更新 locator 指定表。
- 修改前後，目標範圍外的文字與其他 content parts 完全相同；混合 AI 正文、source mapping、manual review、圖片與工具內容不被重建或刪除。
- system order 與 customer_quote 只更新同一已綁定報價，其他報價保持原內容。
- 目標移除、版本失效、跨聊天／跨 user／tenant 的 locator、AI／使用者並發更新與無法核對 mirror 時，不發生部分或誤範圍寫入。
- DB 重新讀回、歷史訊息 API、重新載入聊天及 provider clean representation 各自取得正確版本；成功不能只以畫面刷新判定。

同一個 Mongo 交易及 revision CAS 包含編輯原版／有效列／差異狀態、相關 canonical OCR 或 quotation 狀態、失效資訊及所有受影響訊息文字。AI finalizer、OCR／報價更新與專用 UI 操作共用這個版本範圍；AI 工作使用啟動時讀取的有效 revision，提交前檢查是否已被 UI 編輯取代。一般 message PUT 若試圖改動已受管理的表格，必須導入同一版本服務或拒絕該變更，不能繞過 Steel revision。報價正在使用固定輸入時不改寫它的 immutable checkpoint；UI 操作保留為待核對修改，已完成結果才能成為新的可編輯來源。

顯示用聊天 Markdown 與有效資料的邊界要落實於讀取路徑：`steel/ocr/result.ts` 的既有結果與更新基底、quotation preparation／runner 的訂單輸入、`steel/markdown/completion.ts` 的有效表格處理，以及 Chat／Responses 的 provider message 組裝。Chat／Responses caller 以一次批次讀取或已載入的 managed-table 資料，在送入 AI 前用該 lineage 的有效內容代換受管理 section；不逐則增加串行 DB 查詢。歷史 display 內容保留供 UI，但所有目前計算及後續更新都讀 clean representation。

### 來源關聯的合法狀態

normalized 關聯可為「無檔無頁」「有檔無頁」「有檔有合法單頁」；舊資料只有頁碼文字、沒有可確認檔案時，原文保存在 legacy evidence，normalized 頁碼保持空值並列為未定位。更換或清除檔案先清除舊 normalized 頁碼，避免誤帶另一檔的頁碼；選圖片可明確設定第 1 頁。所有未完整關聯狀態仍可儲存。

來源契約為單值，資料層及 API 不提供多檔／多頁陣列或來源集合，檔案與頁碼 selector 都是單選。選圖片就是單一圖片來源，第 1 頁只是統一的頁面表示，不另綁 PDF。改選來源替換原關聯，不追加第二個來源；加工列從材料繼承同一份單值關聯。舊資料含無法確認的多來源文字只保留為 legacy evidence，不轉成多來源綁定、不任選一個，normalized 關聯保持未定位，仍可閱讀及保存。

同一頁／圖可被多列共同引用，不以來源檔案與頁碼作列唯一鍵，不建立阻止同來源多列的唯一限制。各 row 仍有獨立穩定身分，可分別修改、刪除及復原；查詢目前來源時返回該表全部對應列，不能只取第一列或依來源去重。

來源 cells 不作自由文字編輯；缺少／舊資料待確認的來源可直接使用 selector，可靠來源預設顯示唯讀，使用者判斷舊標記不可靠時用「更正來源」開啟 selector。加工 normalized 來源由材料派生，不能單獨改成另一頁；無法確認舊加工歸屬時保存原始 evidence，待使用者選材料後再派生來源。手動標記只使用同一聊天且可存取的既有檔案與合法頁面，未定位空值不構成錯誤。

## 技術方案提案

| 責任 | 提案 |
| --- | --- |
| 編輯資料保存 | 在 `packages/data-schemas` 的 MongoDB 方法與 schema 分別保存 AI 原文及最新 merge 完整基準、最後人工保存列與完整 Markdown、各自成功更新時間、來源標記、刪除狀態及修訂版本；沿用現有 conversation／quotation 範圍，不另建 Supabase 業務資料流程。 |
| 表格身分 | 邏輯結果綁定 conversation、訊息／content part／table／section owner；AI 完整或 update 改變 AI 基準版本，UI 儲存改變人工 revision，歷史兩者分別保留。 |
| 資料列身分 | 原版列與新增列都有穩定 row ID；相同件號、規格或內容的多列仍獨立，不以來源加件號作唯一鍵。 |
| 材料與加工關係 | 材料列具備穩定身分，加工列保存對應材料 ID；顯示排序可沿用材料後接加工列，但排序不代替綁定關係。舊資料只能在可確認時建立關係，不猜測材料歸屬。 |
| 計算輸入與觸發 | 保存材料計算依據、加工計量模式及明確輸入，區分手動值與依賴結果。依本次完成操作觸發受影響的計算，尊重手動單重／總數；不以歷史備註覆蓋新輸入尺寸。 |
| 可空來源 | `fileId` 與單一原檔頁碼可分別缺值；沒有可確認映射的舊資料保留原文並列為未定位，不以檔名相似、列位置或規格猜測來源。舊跨頁值不能自動挑一頁。 |
| 新 API | shared request／response、query keys 與 data service 放 `packages/data-provider`；讀取表格編輯狀態與提交列操作使用專用契約，包含預期版本及操作 ID。 |
| 服務邊界 | 編輯驗證、版本／狀態判斷、完整表格組裝與 customer_quote 呼叫放 `packages/api`；`api` 只接 auth 與 route wiring。 |
| 一致性保存 | 資料層負責同次提交編輯狀態、canonical state 與相關訊息文字；system order 與 customer_quote 同成同敗。以交易及版本 CAS 保護，不先宣告儲存成功再補寫其餘資料。 |
| 重試與衝突 | 操作 ID 避免重試重複新增／刪除，版本阻止覆蓋 AI 或另一視窗的新結果。衝突保留本地操作，核對最新版後才產生新提交。 |
| 舊資料相容 | 讀取既有 Markdown 與 canonical snapshot；首次編輯時保存原版及建立列身分。未初始化資料的讀取不要求來源完整；舊版資料不得覆蓋最新有效 state。 |
| 前端狀態 | 編輯、檔案／頁面、undo／redo 等 feature-owned 狀態用 Jotai；API 互動用 React Query，成功後更新／invalidate 同一聊天的訊息與表格資料。 |
| 權限及錯誤 | 每次讀寫檢查 user／tenant／conversation、表格及檔案範圍。缺少來源是成功資料；過期版本、真正儲存失敗及無權限使用安全、可本地化的既有或穩定代碼。 |

PDF 預覽需受控單頁渲染，以 selector 決定原檔頁碼；既有 iframe 預覽不能單獨承擔頁面選擇契約。只載入目前所需頁面並清理渲染及 blob 資源，避免多 PDF 全部頁面同時載入。實作時先核對已安裝 PDF 渲染依賴，沿用現有能力；此訪談不指定額外套件或安裝動作。

## 實作與驗證順序

1. 建立有效資料、原版與差異的純函式及 shared 編輯契約，覆蓋重複列、字元 escaping、空來源、單頁標記及刪除線隔離。
2. 加入 data-schemas 編輯保存與版本／操作 ID 契約，覆蓋真實 Mongo 的並發、重試及跨 state／message 保存失敗；訊息與有效結果必須一起提交。
3. 接入 TypeScript 編輯服務與專用 API，重用現有 customer_quote builder；核對已存在報價及後續 AI／OCR 更新能讀取最新有效資料。
4. 接入 Markdown 表格入口、單頁原檔預覽、menu selectors、可編輯列與 undo／redo，覆蓋 keyboard、loading、empty、success、save failure、conflict、readonly 與重新載入。
5. 在修改的 workspace 執行聚焦 Jest、`npx tsc --noEmit`、必要 build、scoped import sorter 與 static checks；訊息載入變更執行專案要求的 Lighthouse。確認 light／dark、窄螢幕及實際多檔預覽。

獨立審查必須包含上方「聊天 Markdown 精準更新」的專項；其未通過時不能把本功能視為完成。

實作前依專案規則完成非例行計畫的 Advisor 審查；實作後對資料一致性、權限及相容性做獨立程式審查。本文不授權提交、推送、發布或 PROD 資料修改。

後續 `implement-spec` 已由使用者明確要求。實作審查補充：已提交相同操作的重試僅回傳保存收據，不進行第二次寫入；未提交操作仍需最後輸出資格，操作 digest 不同不得重用 ID。候選價格從該輸出綁定的客戶快照取得，準備及提交 hash 包含其身分、版本與 tier。新 AI 基準另形成有效覆核／顯示內容，原子更新新 owner 及其衍生結果，但不改最後人工完整 Markdown 或其時間；舊 owner 不被回填。具體契約見完整規格。

## 目前程式的事實與限制

- Markdown 表格共用 `client/src/components/Chat/Messages/Content/MarkdownTableActions.tsx` 的操作列及放大彈窗；檔案預覽在同目錄的 `FilePreviewDialog.tsx`，目前沒有受控 PDF 選頁功能。
- OCR 完整結果與更新由 `packages/api/src/steel/ocr/result.ts` 整理；最新完整狀態保存在 conversation OCR state，來源對照包含檔案 ID、來源代碼與檔名，但沒有穩定資料列 ID 或逐列頁碼關聯。
- system order 更新在 `packages/api/src/steel/quotation/revision.ts` 使用 base hash 與 row index；目前契約只允許修改既有列，新增／刪除材料先經 OCR 修正。
- 現有報價 snapshot 只保存完整 Markdown 及版本資訊，流程中的來源列 ID 未保存為可供 UI 使用的逐列來源關聯。
- 目前沒有直接儲存使用者資料列修改的 Steel HTTP API。新介面需要正式寫入契約與過期版本檢查，不能只修改瀏覽器內的表格。
- 歷史 AI 訊息與最新 canonical 狀態分開保存；現有 state 的版本保護可作為設計依據，但不等於已有通用編輯版本歷程。
- 目前修改前後的刪除線由 `packages/api/src/steel/ocr/result.ts` 產生 `新值 (~~舊值~~)` Markdown，並非現成的前端資料列 diff 元件。現有 cell comments 保存的是瀏覽器草稿與提示詞，不等於 DB 資料編輯。
- `packages/api/src/steel/markdown/quote.ts` 已有確定性的 customer_quote 產生函式：按 system order 每列的品名規格、總數及單價，將總數乘單價後向上取整為小計，再加總可計算的小計。無法計算的列保留空白小計。`quotation/revision.ts` 的既有更新路徑已使用此函式；它不重新查價，也不推導 system order 的重量或計價總數。
- 現有 customer_quote 的計算讀取 `總數` 而不是 `數量`；新需求必須先重算 system order 的重量／總數，再傳入 customer_quote builder，不能只呼叫 builder 當作整套重算。
- 現有 customer_quote parser 不是 diff-aware：帶有刪除線的數字可能被誤讀或無法計算。因此編輯後的有效資料、原版資料與顯示用累積差異需要分開；不得把帶刪除線的聊天表格直接當作目前有效數值或重算輸入。
- 現有 `quotation/weight.ts` 只重算部分具有唯一候選與必要計算依據的 kg 材料，加工列不適用。最終 16 欄表沒有結構化材料綁定、每件加工量／整批量或配料方案；新介面不能只依最終 Markdown 反推這些資料，必須保存及提供明確輸入。
- `repositories/prices.ts` 有 typed 材料／加工候選查詢，候選含 ERP code、productName、specKey、category、material、unit、formulaCode、tierPrices 與重量等依據；目前沒有使用者 catalog HTTP API。SQL 可搜尋型號／品名，但 AI 工具 keyword 契約另有用途限制，UI 應使用專用契約。現有 tier enum 與 A–F 資料型別有 D／E 範圍差異，selector 路徑需按完整 A–F 契約驗證，不擴大為整個既有查價系統重構。

## 設計收斂時要核對的情境

- 一張 OCR 表包含兩份 PDF 與一張圖片；切檔、切頁時只顯示同一張表對應的列，未定位列另列。
- 同一聊天有多版 OCR 與 system order 時，各種類只有最後輸出可修正；舊版唯讀開啟前後的 DB 聊天文本完全相同。一般 Markdown、customer_quote 及同名但未確認身分的表格沒有本功能。
- 新結果在彈窗開啟後完成時，前版不能再保存；偽造 client 資格、直接 API、延遲重試及 undo／redo 均不能改寫舊版。保留未保存操作供核對，不自動寫入最新表。
- 舊列沒有來源或頁碼仍可修改儲存；人工標記來源後才列入對應頁面。
- 修改同一格多次後，比較的是目前值與原版值，而不是最後兩次操作；復原回原值後不殘留差異。
- AI 只輸出 update rows 時，後端 merge 成完整 AI Markdown，未提及列保留；人工保存不污染 AI 基準。AI 更新後以最新完整 AI 基準比較人工覆核內容，歷史原版仍可讀。
- AI 新基準與人工值衝突時保留人工值；採用 AI 操作解除相應人工覆寫。無法確認重複列配對時保留人工組供比對，不丟失修改或重複計價。
- 人工 OCR 較新時下次報價選人工；AI 較新或時間相同時選 AI。AI merge／自動比較不刷新人工保存時間，resume 不切換已固定的來源。
- 新增列帶目前檔案與單頁來源；刪除原版列保留刪除線但不列入有效資料或金額；undo／redo 恢復同一列身分。
- 修改 system order 的總數或單價，自動更新同一報價的 customer_quote 與聊天文字；缺值小計可留空。
- customer tier 為 B、候選只有 A 價時，材料與加工搜尋都顯示 B 價空值；選取後 DB 與聊天單價、小計仍空白，不套用 A 價、舊價或 0。後端不接受 client 偽造 tier；合法 0 價可保存，查價失敗不能轉成空價成功。
- 修改尺寸後更新單重與總重；手動修改單重後保留該值並更新總重；數量變更更新總重與按件計量的加工量，整批量及刀數不錯誤倍乘。
- 刪除材料與加工整組標記，undo 一次復原材料、加工綁定、來源與有效金額；更改加工材料 selector 後來源跟隨新材料。
- 更換材料候選後，既有加工列的身分、材料綁定、候選、輸入、總量與單價完整不變，不重驗或重選；caption 排除未改動加工列。後續獨立修改數量等輸入仍依相應加工重算規則更新。
- 缺少必要計算依據時保留輸入、相關結果留空並可 save，不能用舊總數除以舊數量猜每件加工量。
- 自動儲存失敗時保留修改且可重試；新版已由另一視窗或 AI 保存時，不能覆蓋新版。
- 同列改多格此次 caption 仍為 1 列；材料數量變更影響材料、兩筆加工及三筆客戶報價時，分別顯示 system order 3 列與 customer_quote 3 列。跨頁受影響列也計入；刪除材料計入其加工列，undo／redo 依此次實際變更計數。
- 此次 caption 與後端實際提交及 DB 讀回列差異一致，不使用累積人工差異數；無淨列變更顯示 0，衝突或失敗不顯示已成功更新。
- 聊天重新載入後讀到修改後 Markdown、有效狀態及原版累積差異；關閉彈窗只清除本次 undo／redo 操作歷程。
- 使用相同表格內容建立多聊天、多訊息、多表格及混合 content parts 情境，對照 DB 更新前後，證明只有明確 target 變更，其他聊天內容完全不變。

以上為本次唯讀程式核對的結果，尚未選定新的資料模型或 API 實作方式。
