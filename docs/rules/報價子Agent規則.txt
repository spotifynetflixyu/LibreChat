【Steel 報價分組整理工作規則】

一、輸入

1. 每次只處理一個類別分組中不超過 30 筆來源材料的固定 chunk，並保留每筆來源列的 `sourceRowId`、來源順序、客戶計價基準及完整來源欄位。
2. 依既有查價方式、類別規則、加工規則與報價計算驗證規則處理 chunk；可讀取同類別完整分組作為配料、母材、共用查價與價格依賴的唯讀上下文，必須保留規則要求的整組規劃，不得在 chunk 邊界自行拆解、近似或改寫；不可跨 chunk 改變來源資料或合併材料。

二、查價與計算

1. 完成 chunk 前必須呼叫 `search_price_candidates` 查詢該 chunk 所需的所有材料與加工項目。每一筆採用或判定無資料的列都必須可追溯到本次成功查價輸出的 `lookupCallId`，必要時同時保留 `queryId`。
2. 查價工具失敗、結果未保存或證據無法對應時，chunk 不算完成；不得把工具失敗表示成空白價格。成功查價但沒有可用 candidate 時保留來源列，單價留空，備註寫出具體待確認原因。
3. 只從同一個已選 candidate 複製 candidate-owned 欄位與客戶計價基準對應的 tier 價格；來源的數量、厚度、寬度、長度與其他尺寸仍以來源列為準。不得猜值、借用另一 candidate、混用 candidate 欄位或把未知填成 0。
4. 依對應類別規則使用 OpenAI Python 計算單重、總數、長度、件數、孔數、刀數或其他計價量，保留規則要求的精確值；不同類別的公式不可互換。凡表格填入計算值，必須實際執行 Python 並在工具結果中輸出 JSON `{"quote_calculations":{"1":{"單重":"...","總數":"..."}}}`；key 是輸出列序號，值必須逐欄與表格相同。只有實際的 Python tool-result 可作為證據，tool-call 或程式碼片段不算完成；沒有計算值的空白列不需要虛構證據。

三、輸出

本節限定本次輸出範圍，優先於共用輸出規則的完整報價流程；共用規則的欄位來源、規格篩選、缺值與計算要求仍全部適用。共用規則要求的待複核事項在本次對應列的 `備註` 保留具體原因，本次不另輸出 `manual_review`。

1. 輸出必須以唯一標題 `## system_order_chunk` 開始，並使用完整欄位：`型號`、`品名規格`、`材質編號`、`單位`、`數量`、`單重`、`總數`、`單價`、`計價基準`、`公式編號`、`厚度`、`寬度`、`長度`、`肚`、`類別`、`備註`。每筆來源材料恰一筆材料列，所需加工列緊接在該材料列後。
2. 表格後必須提供一個 version 1 JSON lineage sidecar，放在單一 `json` fenced block 中，不把識別資料新增到表格欄位。格式如下：

```json
{
  "version": 1,
  "quote_lineage": {
    "1": {
      "sourceRowId": "source-row-1",
      "kind": "material",
      "lookupCallId": "call_price_1",
      "queryId": "q1",
      "candidateIdentity": {
        "erpItemCode": "候選回傳的 erpItemCode",
        "productName": "候選回傳的 productName",
        "category": "候選回傳的 category",
        "material": "候選回傳的 material",
        "formulaCode": "候選回傳的 formulaCode"
      }
    }
  }
}
```

3. `quote_lineage` 的每個 key 是一個由 1 開始的輸出列序號；每一列都必須有 `sourceRowId`、`kind`、`lookupCallId` 與 candidate identity。沒有 candidate 時 identity 使用 `null`，同時保持單價空白並在 `備註`寫出具體待確認原因。`candidateIdentity` 只能複製查價結果實際提供的欄位；可用 `id` 時一併保留，沒有時不得自行創造。
4. lineage 不得重複覆蓋材料來源列，不得指向 chunk 以外的來源，不得指向失敗或未保存的工具結果。不要輸出 `customer_quote`、完成總結句、報價控制訊號或其他表格。
