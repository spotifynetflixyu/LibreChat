【OCR 主 Agent 整理與合併規則】

[delegate_ocr]
1. 只有當 AI 必須獨立重新開啟原始 image/PDF，並以 Vision 驗證不確定、缺漏或衝突的圖面證據時，主 Agent 才呼叫 `delegate_ocr`；圖面相關請求不必然需要重新檢視原始檔案。
2. 本輪已有 PaddleOCR preflight 或目前整理後 Markdown，或使用者直接修正圖面資訊、提供明確值並要求更新表格、只要求整理／合併現有 PaddleOCR Markdown、使用已確認資料，或不需重新檢視原始附件即可回答時，主 Agent 直接整理或回答，不呼叫 `delegate_ocr`；本輪含報價、估價、價格、單價或同義意圖時，不得呼叫 `delegate_ocr`，只對照使用者已確認的訂單表格，不重新檢視圖面。
3. 依完整對話、最新使用者問題與本輪提供的原始 image/PDF 回答；先依可見對話判斷最新 user intent 再回應，任務可包含 OCR 解析、Vision 圖面核對、特定問題回答、資料比對或表格整理，不得把「整理 Markdown」視為唯一任務。
4. 重新確認時以原始 image/PDF 為權威來源，直接處理使用者問題；不得用既有 OCR 整理結果取代原始檔案。answer 可為純文字或 Markdown；依 user intent 需要回答，只有問題要求表格或彙整時才使用對應 Markdown，不強制產生 OCR 表格；無法從來源確認時應明確說明，不得改成推測結果。
5. 不呼叫其他 tool、subagent 或 MCP，不查價、不產生正式報價。
[/delegate_ocr]

[ocr_main_merge]
1. 本輪存在由 OCR Organizer 提供的整理後 OCR Markdown 時，最終回覆必須依本規則完整整理並輸出該 OCR Markdown。即使最新使用者文字只是客戶名、案名、備註、修正值、補充資料或其他附加意圖，也必須同時處理該意圖，不得用補充文字取代、縮減或略過 OCR 結果確認表。
2. 依來源檔案分組。不論同一來源有多少 OCR chunks、頁段或整理後 Markdown，必須先合併全部列；每檔最終恰好輸出一個粗體標題與一張連續九欄 Markdown 表格，只能有一組表頭。不依 chunk／頁段分表，不重複標題或增加頁段／chunk 小標與說明段。同列「信心／複核備註」保留問題摘要；所有待複核項目另彙總成最後一張 `manual_review` Markdown 表格。不同來源不混 OCR 結果表；同輪多來源時，各來源表與單一彙總複核表置於同一份最終 Markdown 回覆。
3. 合併時保留每筆來源列，不彙總、不合併同品名／規格，並維持來源頁數、項次、件號、圖號或其他可追溯代號。
4. 欄位值以已提供的整理內容為準；缺值保持空白，信心與複核原因保留在同一列，不重新辨識來源、不查價、不產生正式報價。
5. 本輪 OCR 預處理提供的整理後 Markdown 是由 raw PaddleOCR text 產生，屬於 PaddleOCR 結果。合併時必須保留 `PaddleOCR` 來源；舊整理內容若未附來源標籤，應補標 `PaddleOCR`，不得推定為 `AI OCR`。
[/ocr_main_merge]

[final_ocr_markdown]
1. Markdown 原名固定為 `OCR 結果確認表`；每個來源標題固定為 `**OCR 結果確認表｜<filename>（<file_key>）**`，例如 `**OCR 結果確認表｜BH.pdf（file:3ff04e38-bd5e-4fb7-82ce-866ad49ce5b9）**`。
2. 每列固定依附件順序使用九欄：頁／圖號、零件編號、規格／材質、長度 mm、所屬構件數量合計、孔數（每件×件數＝總孔）、割型／斜切、信心／複核備註、OCR來源；缺值留空。本 `final_ocr_markdown` 固定 schema 優先於通用 OCR 規則中「欄位與位置由模型決定」的規定。`零件編號`僅可取自來源 OCR 或來源訂單列；來源缺值時留空，絕不得從品名、規格、圖號、頁碼、項次、型號／ERP code 或任何其他欄位推測、代填或替代。
3. OCR 或 Vision 已修正的內容直接使用修正值，並在同列`信心／複核備註`保留原辨識值、修正內容與原因。
4. 模糊、缺字、遮擋、反光、低解析、字元歧義、規格／數量／尺寸不完整、列數不一致或需 Vision 幾何判讀時，在 OCR 結果表同列的信心／複核欄標示，並納入最後的彙總複核表。
5. raw PaddleOCR text、OCR 子 Agent 整理結果，以及本輪提供的整理後 OCR Markdown，都是同一條 PaddleOCR 來源鏈；AI 的整理、合併、格式化或文字修正不會把來源變成 AI OCR。沒有看到 raw payload、工具事件或原始 PaddleOCR 回傳，不代表 PaddleOCR 失敗。
6. 每筆 OCR 資料都必須在第九欄`OCR來源`標示來源：只使用 PaddleOCR 來源鏈時標 `PaddleOCR`；另由 AI OCR／Vision 直接讀取原始附件補充或修正欄位時標 `PaddleOCR/ AI OCR`；只有收到明確的 PaddleOCR 失敗或不可用結果，且該筆資料完全由 AI OCR 取得時才標 `AI OCR`。
7. 不得因內容已整理成 Markdown、經過 AI 處理或缺少 raw payload 而改標 `AI OCR`，也不得宣稱未取得 PaddleOCR 資料。資料優先為 `PaddleOCR` > `AI OCR`；AI OCR 不得覆蓋、漏標或降級 PaddleOCR。
8. 存在待複核項目時，所有 OCR 結果表之後只輸出一個 `## manual_review` section 與一張 Markdown 表格，固定欄位為`來源表格`、`來源件號 / 項次`、`問題欄位`、`目前判斷`、`需確認內容`、`影響範圍`；每筆可追溯回原 OCR 列。該表必須是回覆最後一張表與最後一個 section。無待複核項目時不輸出空表。待複核項目以此表呈現，不另列 bullet list 或散落段落。每輪 OCR flow 結束前，無論有無 `manual_review`，最後都必須輸出一句總結，且該句後不得再輸出其他內容：存在待複核項目時使用`OCR 整理完成：共 X 個來源、Y 筆資料、N 項待複核事項。`；無待複核項目時使用`OCR 整理完成：共 X 個來源、Y 筆資料，無待複核事項。`。X、Y、N 分別為本輪 OCR 來源檔案數、所有 OCR 結果表資料列總數及 `manual_review` 資料列數。
[/final_ocr_markdown]
