【OCR 結果合併流程規則】

[ocr_main_merge]
合併本輪提供的整理結果 Markdown，依鋼材種類判斷規格檢查更新列的類別一致性，並產生最終表格；不重新執行 OCR、Vision 或圖面判讀。

【前提與規則】

1. 不需要也不得使用 OCR 或 Vision 重新讀取、辨識或判讀原始 image/PDF；只處理本輪提供的 metadata 與 Organizer Markdown，不得要求或使用 file URL。
2. 每個檔案的 metadata keys 為 `source_code`、`source_filename`、`file_key`、`page_ranges`、`chunk_count`。`source_code` 是檔案代號；同一檔案的所有 chunks、retry 與 split 都使用同一個 `source_code`，不得依 chunk 另行編號。`source_filename` 必須保留完整原始檔名與副檔名，例如 `PL.pdf`，不得省略、改寫或推測副檔名。
3. `source_file_mapping` 是本輪的檔案對照 metadata；其每個項目只包含 `source_code` 與 `source_filename`。`source_filename` 只表示使用者原始上傳檔名；缺少時留空，不得以 `file_key`、storage key、filepath、URL 或雜湊值代替。
4. `來源` 只表示檔案代號，值只能逐字使用 `source_code`。`OCR來源` 只表示引擎來源；兩者不可混用。
5. 本輪存在任何 OCR 整理後 Markdown、預處理合併結果或 OCR chunks 時，包含 PaddleOCR 部分失敗時其他成功頁段的整理 Markdown 與 file metadata，首次建立 `ocr_result` 時必須完整輸出；已有 `previous_ocr_result_markdown` 時以 `## ocr_result_updates` 只輸出本輪新增或修改列，未修改列不輸出；附加的客戶名、案名、備註、修正值或其他意圖也須同時處理，不得遺漏本輪新增或修改列。
6. PaddleOCR text、整理結果與本輪提供的 OCR Markdown 都是同一條 PaddleOCR 來源鏈；整理、合併、格式化或文字修正不改變來源。
7. 最終 Markdown 的 section 名稱是固定 machine title，必須逐字使用 `source_file_mapping`、首次完整表 `ocr_result` 或修正表 `ocr_result_updates`、`manual_review`；不得翻譯、改名、增刪前後綴或改用中文顯示標籤，並且必須使用精確的 `## <name>` H2 格式。
8. 提供 `previous_ocr_result_markdown` 時，該內容是本輪更新前的完整 OCR 結果基底；提供 `suggested_ocr_result_columns` 時，依原順序優先沿用其欄位。Organizer Markdown 明確新增必要欄位時可加入，不得為了套用建議欄位而刪除新資料。

【工作流程】

1. 先讀取 `source_file_mapping`，保留每組 `source_code` 與 `source_filename` 對照，不得重新編號、臆造或用檔名代替代號。
2. 再依每個檔案 metadata 的 `source_code`、`page_ranges`、`chunk_count` 將 chunks、頁段與 Organizer Markdown 排序；同一檔案的所有資料列都填同一個 `source_code`。
3. 先盤點所有來源實際出現的欄位與同義欄位，保留下方規定的固定欄位，將同義欄位統一至固定欄名；其餘欄位依使用者意圖與資料內容規劃，不遺失既有值與規格資訊。
4. 沒有既有結果時，將本輪所有檔案資料列整理為一張完整 `ocr_result`。已有 `previous_ocr_result_markdown` 時，以 `## ocr_result_updates` 修正表只輸出本輪新增或修改列，沿用既有欄名與順序，每列保留全部欄位及未修改值，不重複輸出未修改列。省略不表示刪除，空白儲存格表示將該欄設為空白，不能用來代替未修改值。相同識別有多筆獨立列時，輸出該組全部列及全部既有欄位，保留各列頁碼、尺寸等識別資訊，不得只輸出部分列。不合併同品名或規格，不彙總，不依檔案、chunk 或頁碼拆表。
5. 每列保留來源、頁碼、零件編號。Organizer Markdown 或既有 OCR 結果已提供原始檔案頁碼時，直接保留，不得再次加上 `pageStart`。只有明確標示為 chunk 內頁碼時，才依對應的 `page_ranges` 換算，公式為「原始頁碼 = pageStart + chunk 內頁碼 - 1」；例如 `page_ranges` 為 51–100 時，chunk 內 `p.1` 換算為 `p.51`，已是原始頁碼的 `p.51` 仍保留 `p.51`。最終只輸出原始頁碼，不並列分塊內頁碼；無法確認頁碼基準時不得猜測換算，保留原值並納入 `manual_review`。
6. 加工確認結果整合進唯一的 OCR 結果表，不另建 Vision 表；依實際內容自主加入加工欄位，保留每項的加工、數量、總量、判斷依據與信心／複核原因。
7. 只有依來源、原始頁碼、列位置或其他可追溯資訊，確認為同一來源列的重複辨識時才合併，本輪確認的新值整合回該原資料列。不得只因 `來源` 與 `零件編號` 相同而合併；不同尺寸、不同來源列或獨立訂單列須分別保留，即使品名、規格或零件編號相同。無法確認是否為同一來源列時保留各列並納入 `manual_review`。`來源` 或 `零件編號` 缺值時不得猜測補值。
8. 固定依 `[最終 Markdown 輸出順序]` 輸出；不輸出逐頁標題、逐頁表格、尺寸／加工 bullet list、分隔線、解釋文字或額外重複表格。

【類別複核】

只檢查本輪更新列內已提供的明確文字。若 `RH250×125×6×9` 被 AI 填為扁方管，可依 RH 直接修正為 H型鋼；若原始品名真的寫「方管」而斷面卻寫 RH，屬來源衝突，類別留空並列入 `manual_review`。不得將 AI 舊類別誤當原始來源品名，也不得猜測遺失前綴或以相鄰列補值。本輪未更新的既有列不需輸出。

[final_ocr_markdown]
[最終 Markdown 輸出順序]

1. `## source_file_mapping`
   - 必須是第一個 section 與第一張 Markdown 表格。
   - 欄位固定且只能是`來源`、`檔名`。
   - 逐列複製 `source_file_mapping` 的 `source_code` 與 `source_filename`，依 mapping 順序輸出，不得重排、改寫、重新編號或臆造。
   - `來源` 填 `source_code`；`檔名` 填包含完整副檔名的 `source_filename`。任一值缺少時留空，不得以其他 metadata 補猜，不得省略或改寫副檔名。
   - 單檔例：`source_file_mapping` 項目為 `source_code=F1`、`source_filename=PL.pdf`，對照列為 `| F1 | PL.pdf |`。
   - 多檔例：mapping 項目依序為 `F1=PL.pdf`、`F2=BH.pdf`，對照列依序為 `| F1 | PL.pdf |`、`| F2 | BH.pdf |`。

2. 首次 `## ocr_result`；已有完整結果時改用 `## ocr_result_updates`
   - 必須緊接在 `source_file_mapping` 後，只輸出一張連續表格，全部檔案共用一組表頭。首次輸出完整資料；修正時只輸出變動列並沿用既有欄位。沒有變動列時只保留表頭與分隔列。AI 不得同時輸出完整表與修正表。
   - 固定包含 `來源` 及 `類別`、`零件編號`、`品名規格`、`厚度`、`長度`、`寬度`、`數量` 欄位，欄名逐字使用，不改名、合併或省略；缺值保留欄位並留空，不填 0 或猜測。其他欄位依使用者意圖與來源資料規劃，不取代固定欄位。
   - `品名規格` 保留來源完整品名與規格，不得遺失原始規格資訊。
   - `來源` 只能逐字填入該檔案 metadata 的 `source_code`；不得填 `source_filename`、`file_key` 或自行發明的代號。同一檔案的所有 chunks、retry 與 split 結果都填同一個值。
   - `類別` 依鋼材種類判斷規格檢查本輪 Organizer Markdown 的更新列；同列訂單材料規格（完整斷面代碼、尺寸語意或規格內明示的產品名稱）足以唯一確認時，可修正錯誤類別或補入缺值，保留原值、修正值與規格依據。零件編號只輔助定位及對照，不用於分類。缺乏明確規格證據或來源互相衝突時留空並納入 `manual_review`，不得猜測；本輪未更新的既有列不需輸出。
   - `零件編號` 只能取自來源 OCR 或來源訂單列；缺值留空，不得由品名、規格、頁碼、或其他欄位推測代填。
   - `OCR來源` 只填引擎來源：只使用 PaddleOCR 來源鏈時標 `PaddleOCR`；PaddleOCR 與模型內建 OCR／Vision 補充或更正結果共同採用時標 `PaddleOCR/ AI OCR`；完全由模型內建 OCR／Vision 取得時標 `AI OCR`；兩者都未取得時留空。Vision 只確認既有 PaddleOCR 值而未補充或更正時，仍標 `PaddleOCR`。
   - `厚度`、`長度`、`寬度` 統一以 mm 表示，來源已明示的單位須正確換算並保留依據；欄名統一為 `厚度`、`長度`、`寬度`，不另用帶單位的同義欄名。
   - `厚度`、`長度`、`寬度`、`數量` 每格只能填一個整數或小數，不得含文字、單位、千分位逗號、近似符號、範圍、多個候選值或算式；保留有效小數，缺值留空，不用 `0` 或文字代替。原值、單位換算、加總算式與複核原因保留於同列備註／加工／複核資訊；例如來源已確認 `4+1+2+1+1` 件，數量填 `9`。
   - 輸出前對本輪新增或修改列執行四個數字欄的格式檢查；未修改列不重新輸出，只能依該列已提供的明確數值與斷面語意整理，保留全部來源列及原始資訊，不重新辨識或推測。無法確認單一數值時該格留空，原文移至同列備註並納入 `manual_review`，不得任選範圍端點或第一個候選值。
   - 若欄位有 `尺寸(mm)` 和 `長度`，可同時有值。`尺寸`已明確表示二維成品尺寸`寬×長`，且`長度`空白時，保留完整`尺寸`，並將`×`後最後一個數值同步填入`長度`。例如：`600×650`填入長度`650`。
   - 來源或 Organizer Markdown 已明示`長度`時，以明示值為準，不得用`尺寸`覆寫。
   - OCR 或 Vision 已修正的內容直接使用修正值，並在同列保留原辨識值、修正內容與原因；模糊、缺字、遮擋、反光、低解析、字元歧義、規格／數量／尺寸不完整、列數不一致或需幾何判讀時，標示信心／複核資訊並納入 `manual_review`。

3. `## manual_review`
   - 只在存在待複核項目時輸出；無待複核項目時不輸出空表。
   - 必須位於 OCR 結果表之後，且是最後一張表格與最後一個 section。
   - 欄位固定為`來源`、`頁碼`、`零件編號`、`問題欄位`、`目前判斷`、`需確認內容`、`影響範圍`。
   - `來源` 只能逐字填入該檔案 metadata 的 `source_code`；不得填 `source_filename`、`file_key` 或自行發明的代號。
   - 不列出`單重`、`總重`、`孔徑`、`材料`或`材質`的確認。
